## 1. 한눈에 보는 현재 상태

MODIZA는 대구 지역의 커뮤니티 참여자, 커뮤니티 운영자, 공간 운영자, 관리자를 연결하는 플랫폼이다. 현재는 단순 UI 시안이 아니라 인증, 역할별 권한, 데이터 저장, 운영 화면, 관리자 심사, AI 보조 기능까지 연결된 MVP 단계다.

| 영역 | 현재 판단 | 설명 |

| 전체 기능 범위 | 약 80% 구현 | 핵심 사용자와 운영자 흐름 대부분의 코드가 존재함 |
| 출시 준비도 | 약 60~65% | 실제 서비스 전 오류 수정, 테스트, 약관, 신고 접수, 보안 점검 등이 필요함 |

## 2. 상태 표기 기준

- **구현**: UI와 데이터 처리 코드가 연결되어 있고 해당 화면 또는 핵심 조회가 확인됨
- **부분 구현**: 주요 코드가 있지만 데이터 부재, 실제 외부 호출 미검증, 또는 일부 후속 기능이 없음
- **오류 확인**: 구현은 되어 있으나 현재 재현 가능한 오류가 있음
- **미구현**: 화면, API, 데이터 구조 중 핵심 요소가 없음

이 문서에서 “구현”은 곧바로 “운영 환경에서 모든 예외 상황까지 검증 완료”를 의미하지 않는다.

## 3. 사용자 역할과 접근 권한

한 계정에 여러 역할을 동시에 보유할 수 있다.

| 역할 | 획득 방식 | 주요 권한 |
|---|---|---|
| `member` | 모든 가입자에게 기본 부여 | 커뮤니티 탐색, 신청, 찜, 알림, 프로필 관리 |
| `community_host` | 운영자 프로필 작성 후 자체 활성화 | 커뮤니티 등록·관리, 신청자·일정·체크리스트 관리 |
| `host_pending` | 공간 운영자 자격 신청 중 내부 상태 | 공간 운영자 승인 대기 |
| `space_host` | 관리자 승인 | 공간 등록, 공간별 인증 신청, 이용 요청·예약 관리 |
| `admin` | DB 또는 관리자 절차로만 부여 | 모든 관리자 화면과 운영 조치 |

권한 보호 방식:

- 페이지는 Server Component layout에서 로그인·역할을 확인한다.
- API는 서버에서 세션과 프로필 상태를 다시 확인한다.
- Supabase RLS가 소유자 ID와 역할을 기준으로 행 접근을 제한한다.
- 관리자용 Service Role Key는 서버에서만 사용하며 브라우저로 전달하지 않는다.
- 정지된 계정은 보호된 API 사용이 차단된다.
- 커뮤니티 운영 권한과 공간 운영 권한은 관리자가 회수할 수 있다.

## 4. 공개 방문자 기능

### 4.1 홈 `/`

**상태: 구현**

- 서비스 소개와 주요 진입 버튼
- 관심사 카테고리 탐색
- 추천 커뮤니티 노출
- 모집 중 커뮤니티 노출
- 새 커뮤니티 노출
- 이번 주 모임 카드
- 지역별 탐색 진입
- 커뮤니티 운영자·공간 운영자 유입 배너
- 로그인 사용자의 관심사 기반 추천과 찜 상태 표시

주의: 홈의 여러 섹션은 동일한 공개 커뮤니티 목록을 잘라서 보여주는 방식이 포함되어 있어, 향후 운영 기준에 맞는 별도 랭킹·큐레이션 정책이 필요하다.

### 4.2 커뮤니티 목록 `/communities`

**상태: 구현**

- 텍스트 검색
- 카테고리 필터
- 지역 필터
- 추천순 등 정렬
- 모집 상태와 남은 인원 표시
- 찜 버튼
- URL 쿼리를 통한 카테고리·지역 진입

검색과 필터는 현재 받아온 공개 커뮤니티 배열을 브라우저에서 가공한다. 데이터가 커지면 서버 검색, 페이지네이션, 전문 검색 도입 여부를 결정해야 한다.

### 4.3 커뮤니티 상세 `/communities/[slug]`

**상태: 구현**

- 정원, 현재 인원, 참가비
- 모임 방식과 주기
- 추천 대상, 활동 설명, 준비물, 규칙, 태그

- 참여 전 확인사항
- 로그인 기반 참여 신청

## 7. 커뮤니티 운영자 기능

### 7.1 운영자 시작 `/community-host/start`

**상태: 구현**

- 기존 회원 계정을 유지한 채 운영자 역할 추가
- 운영자 소개, 활동 지역, 관심 카테고리, 운영 스타일 등록
- 회원 닉네임·사진과 운영자 프로필 연동
- 권한 회수 상태 차단과 사유 표시

### 7.2 커뮤니티 등록

**상태: 구현**

진입 경로:

- `/communities/register`: 등록 방식 선택
- `/communities/register/with-modiza`: AI 초안 생성 후 편집
- `/communities/register/write`: 직접 작성

등록 정보:

- 이름, 카테고리, 한 줄 소개, 상세 소개
- 참여 대상, 최대 인원, 참가비
- 활동 설명, 분위기, 필요한 시설
- 실내·실외, 음식·음료 필요 여부
- 예상 활동 시간, 예산, 이동 가능 범위
- 다음 일정과 지역
- 모집 질문, 태그, 모임 주기
- 추천 대상, 참여 전 안내
- 대표 이미지와 활동 사진
- 추천 공간 선택 또는 장소 없이 등록

기타 구현:

- 작성 중 브라우저 임시 복구
- 임시 저장과 공개 등록
- 대표 이미지 5MB 제한
- 활동 사진 최대 8장
- 등록 후 오픈채팅 설정 단계

### 7.3 AI 커뮤니티 초안

**상태: 부분 구현**

- 아이디어, 참여 대상, 분위기, 인원, 주기를 질문한다.
- OpenAI 구조화 출력으로 이름, 소개, 모집 글, 질문, 태그 초안을 만든다.
- 생성 결과는 운영자가 수정한 뒤 등록한다.
- 코드와 환경변수는 준비돼 있으나 이번 점검에서는 실제 유료 OpenAI 호출을 실행하지 않았다.

### 7.4 내 커뮤니티 관리 `/dashboard/communities`

**상태: 구현**

- 현재 계정 소유 커뮤니티만 조회
- 상세 정보 수정
- 공개·비공개 전환
- 모집 시작·마감
- 운영 중지
- 신청자, 일정, 체크리스트, 공간 요청 화면 이동
- 오픈채팅 링크 등록·수정·삭제

데모 커뮤니티 12개는 의도적으로 `owner_id = null`이므로 일반 운영자 계정의 “내 커뮤니티”에는 나타나지 않는다. 관리자는 관리할 수 있다.

### 7.5 운영 대시보드 `/dashboard?view=community`

**상태: 구현**

- 운영 중 커뮤니티 수
- 승인 대기 신청 수
- 7일 이내 일정
- 미완료 준비 항목
- 커뮤니티별 상태와 운영 경고
- 오늘 처리할 업무 자동 구성
- 최근 신청, 다음 일정, 체크리스트 진척도
- 오픈채팅 미등록, 장소 미확정, 신청 대기, 일정 임박 안내
- 공지 작성 도구

### 7.6 신청자 관리 `/dashboard/applications`

**상태: 구현**

- 운영자가 소유한 커뮤니티의 신청만 조회
- 커뮤니티·상태별 필터 진입
- 신청자 이름, 연락처, 자기소개, 동기, 답변 확인
- 참가 승인·거절
- 처리 중 정원 재검사
- 신청자에게 사이트 알림 생성

### 7.7 일정 관리 `/dashboard/schedules`

**상태: 구현**

- 커뮤니티별 일정 추가·수정·삭제
- 날짜, 시작·종료 시간, 장소, 설명
- 운영자 소유권 기반 RLS
- 참가자 안내문 AI 제안
- 모임 진행 순서 AI 제안·편집·저장

일정 자체와 진행 순서는 구현되어 있으나 반복 일정 자동 생성과 캘린더 외부 연동은 없다.

### 7.8 체크리스트 `/dashboard/checklists`

**상태: 구현**

- 커뮤니티별 체크리스트 그룹 생성
- 항목 추가·수정·삭제
- 완료 상태 전환
- 진행률 표시
- AI 준비 항목 제안
- 제안 항목 선택·문구 편집 후 실제 체크리스트에 추가

### 7.9 참가자 공지·안내문

**상태: 부분 구현**

- 신청 승인, 첫 모임, 하루 전, 당일, 장소·시간 변경, 준비물, 모집 마감, 취소, 종료 감사 유형 지원
- 말투와 길이 선택
- AI 제안 결과 직접 수정
- 클립보드 복사

공지의 자동 발송 기능은 없다. 운영자가 복사해 오픈채팅 등 외부 채널에 직접 전달하는 구조다.

### 7.10 오픈채팅

**상태: 구현**

- 운영자의 카카오 오픈채팅 URL 등록·수정·삭제
- 참가 승인된 사용자만 링크 조회
- 링크 등록 시 대상 사용자에게 알림 생성

카카오톡 API를 이용한 메시지 발송이나 방 생성 자동화는 없다.

### 7.11 커뮤니티용 공간 추천

**상태: 구현**

- 커뮤니티 작성 정보로 공간 추천
- 인원, 시설, 활동, 지역, 분위기, 가격, 요일 기준
- 최대 인원 부족, 필수 시설 없음, 선택 요일 이용 불가 시 제외
- Top 5 반환
- 선택 공간을 커뮤니티에 연결
- 조건을 완화해 다시 추천

별도의 `/dashboard/spaces/recommend` 화면에서도 조건을 직접 입력해 추천받을 수 있다.

### 7.12 공간 이용 요청

**상태: 구현, 라이브 데이터 미검증**

- 커뮤니티 운영자가 공간 상세에서 커뮤니티를 선택
- 목적, 날짜, 시간, 예상 인원, 메시지를 입력해 요청
- 일반 이용 요청과 협의 요청 구분
- 보낸 요청 상태와 공간 운영자 메모 확인
- 승인된 요청을 커뮤니티 운영자가 최종 예약 확정

현재 라이브 DB에는 공간 이용 요청과 예약 데이터가 각각 0건이라 실제 계정 간 전체 왕복 흐름은 데이터로 확인되지 않았다.

## 8. 공간 운영자 기능

등록 정보:

현재 라이브 DB에는 공간별 인증 신청 데이터가 0건이다. 기존 데모 공간 4개는 모두 승인 상태다.

## 10. AI 기능 정리

| 기능 | 입력 | 출력/사용 방식 | 현재 상태 |
|---|---|---|---|
| 커뮤니티 초안 | 아이디어, 대상, 분위기, 인원, 주기 | 소개·모집 글·질문·태그 초안 | 코드 구현, 실제 호출 미검증 |
| 공간 사진 분석 | 사진 5~10장 | 시설·분위기·인원·활동 등 구조화 분석 | 코드 구현, 라이브 저장 0건 |
| 공간 추천 | 인원·지역·예산·시설·분위기·요일 | 규칙 기반 Top 5와 AI 설명 | 규칙 엔진 확인, AI 설명 호출 미검증 |
| 참가자 안내문 | 커뮤니티·일정·안내 유형·말투 | 제목과 본문 초안 | 코드 구현, 자동 발송 없음 |
| 체크리스트 제안 | 일정·범위·활동·제외 항목 | 그룹별 준비 항목 | 코드 구현, 선택 후 저장 |
| 진행 순서 제안 | 일정 시간·목적·활동·분위기 | 시간대별 진행 순서 | 코드 구현, 편집 후 저장 |

공통 정책:

- OpenAI 모델은 `gpt-5.4-mini`로 설정돼 있다.
- Responses API와 Zod 구조화 출력을 사용한다.
- 브라우저에 OpenAI 키를 노출하지 않는다.
- 운영 AI는 `ENABLE_OPERATION_AI=true`일 때만 UI에 노출한다.
- AI 제안은 자동 저장하지 않고 사용자가 적용해야 반영된다.
- 공간 추천 순위는 AI가 아니라 규칙 엔진이 결정한다.
- 추천 설명은 조건과 결과 해시를 기준으로 DB 캐시한다.
- 운영 AI에는 신청자 이름·이메일·연락처·답변을 전달하지 않도록 구성돼 있다.

## 11. 공간 추천 규칙

추천 점수는 최대 100점이다.

| 항목 | 배점 |
|---|---:|
| 인원 | 25 |
| 필수 시설 | 20 |
| 적합 활동 | 20 |
| 지역 | 15 |
| 분위기 | 10 |
| 가격 | 5 |
| 이용 요일 | 5 |

즉시 제외 조건:

- 공간 최대 인원이 요청 인원보다 적음
- 필수 시설 중 하나라도 없음
- 선택 요일에 이용 불가
- 공간 상태가 승인·공개 상태가 아님

동점이면 시간당 가격이 낮은 공간, 최근 등록 공간 순으로 정렬하고 최대 5개를 반환한다.

## 17. 확인된 미구현·부분 구현·오류

### 우선순위 P0: 다음 개발 전에 해결 권장

1. **비로그인 공간 상세 RLS 오류**
   - 공개 상세 페이지가 일부 비로그인 요청에서 `42501`로 실패한다.
   - 공개 정책에서 관리자 확인 함수를 호출하는 구조를 역할별 정책으로 분리하는 방식이 적합하다.

2. **DB migration 이력 부재**
   - 로컬 SQL 파일 35개는 존재하지만 Supabase migration 이력 조회 결과는 0개다.
   - 동일 프로젝트에서 개발을 계속하는 데는 지장이 없고 기존 SQL을 다시 실행하면 안 된다.
   - 앞으로의 DB 변경부터 migration으로 적용·기록하고, 별도 작업으로 현재 원격 스키마 기준선을 정리해야 한다.

3. **자동화 테스트 부재**
   - 단위·통합·E2E 테스트가 없다.
   - 역할과 RLS가 복잡하므로 권한 회귀를 수동 테스트만으로 막기 어렵다.

### 우선순위 P1: 출시 전에 필요

1. 이용약관과 개인정보처리방침 링크가 `#` 임시 링크다.
2. 사용자 신고 접수 UI·API가 없다.
3. Supabase Security/Performance Advisor 경고를 출시 기준에 맞게 분류·해결해야 한다.
4. 공간 등록·인증·이용 요청·예약의 실제 두 계정 왕복 테스트가 필요하다.
5. OpenAI 기능별 정상·실패·시간 초과·비용 제어 검증이 필요하다.
6. 업로드 파일의 실제 버킷 정책과 MIME·용량·삭제 흐름을 역할별로 검증해야 한다.
7. 운영 로그, 오류 추적, 서비스 상태 모니터링 도구가 없다.

### 우선순위 P2: 제품 확장 후보

1. 공간 공개 목록·검색·지도 탐색

## 20. 인수인계 결론

현재 MODIZA에서 새 기능 개발을 이어가는 것은 가능하다. 인증과 역할, 커뮤니티 운영, 공간 운영, 관리자 심사라는 핵심 도메인 골격이 이미 구축돼 있다.

다만 이후 기획은 아래 세 종류를 구분해야 한다.

1. **기존 기능 안정화**: 공개 공간 RLS, 테스트, migration 기준선, 보안·성능 경고
2. **출시 필수 보완**: 약관, 신고 접수, 모니터링, 실제 계정 간 E2E 검증
3. **새 제품 기능**: 결제, 후기, 공간 검색, 메시징, 알림 채널, 출석·정산

기존 데모 커뮤니티와 공간은 공개 탐색용 샘플이며 소유자 없는 상태가 정상이다. 새 기능은 실제 사용자 소유 데이터 기준으로 설계하고, 데모 데이터는 별도 예외로 유지하는 것이 안전하다.
